There are exactly four code paths that can write a record to the dead-letter file, and all four funnel through `write_dead_letter`, the only function that actually writes to `config.DEAD_LETTER_PATH`.

The first path is the normal pipeline failure path: in `relay/pipeline/orchestrator.py`, `run_pipeline`'s `except RelayError` block calls `write_dead_letter` whenever `should_retry` returns false, which covers both an immediately non-retryable exception and a retryable one whose attempts have been exhausted. The second path is `relay/pipeline/scheduler.py`'s `expire_stale`, which calls `write_dead_letter` for any retry that has been sitting in the scheduler's queue longer than `RETRY_STALE_TIMEOUT_S`, giving up on it without ever running its callback. The third path is manual: `main.py`'s `run_quarantine` command lets an operator dead-letter a raw event directly from the CLI, bypassing the pipeline entirely, and it also calls `write_dead_letter`. The fourth path is also in `main.py`, inside `run_demo` itself: each raw payload is pushed onto a bounded `InMemoryQueue` before being popped and processed, and if that push raises `QueueFullError` because the inbox is already at capacity, `run_demo` dead-letters the raw payload directly rather than dropping it silently, again by calling `write_dead_letter`.

Two things are worth flagging as near-misses that do NOT belong on this list. First, `write_dead_letter` itself calls `log_sink.log_dead_lettered` at the end, so a dead-letter event always produces a matching log line -- but `log_dead_lettered` only emits a log message and never opens or writes to the dead-letter file itself, so it is not a fifth write path. Second, `Scheduler.drain_ready` -- the sibling method to `expire_stale` on the same class -- does not dead-letter anything: when a scheduled retry's callback raises unexpectedly, `drain_ready` just logs the exception and skips to the next one, rather than calling `write_dead_letter`. It's easy to assume both scheduler exit doors behave the same way, but only `expire_stale` writes to the dead-letter file.

(`main.py`'s `run_replay` is not counted separately either -- it just re-invokes `run_pipeline` on each dead-lettered record, so any resulting dead-letter write happens through the same orchestrator except-block as path one, not through a call inside `run_replay` itself.)
