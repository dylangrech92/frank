Running `python3 main.py demo` reads each raw record out of `sample_events.jsonl` and pushes it onto an `InMemoryQueue` before popping it back off and handing it to `run_pipeline`, one event at a time.

From there the event moves through five stages in order. First, `ingest` calls `build_order_event`, in `relay/handlers/ingest.py`, which is the only place in the whole codebase that constructs a fresh `Event` with a newly generated id. Next, `run_transform` calls `bus.publish(EVENT_ORDER_CREATED, event)`, and that publish is what triggers `normalize_event` to trim and coerce the payload's fields. Then `validate` calls `validate_order` and, once the order passes, publishes `EVENT_ORDER_VALIDATED`, which triggers `record_validation` in `relay/handlers/audit.py`. After that, `enrich` dynamically loads the configured plugin by calling `load_plugin(config.ENRICHMENT_PLUGIN)` -- an `importlib.import_module` call rather than a static import -- runs its `enrich` function, and publishes `EVENT_ORDER_ENRICHED`, so `record_enrichment` also fires from the same audit module.

Finally, `deliver` hands the event to `finalize_and_send`, in `relay/handlers/delivery.py`. Before dispatching to a sink, `finalize_and_send` calls `clean_event(event)` -- the aliased `normalize_event` imported from `relay/compat/legacy.py` -- so the payload is normalized a second time right before delivery, not just once back at the transform stage. Only after that does it dispatch through `SINK_DISPATCH` keyed by `config.DELIVERY_SINK`. Under the default configuration that key is `"file"`, so the call resolves to `send_to_file_sink` in `relay/sinks/file_sink.py`, and that is where the event is actually persisted -- appended as a JSON line to `delivered.jsonl`. The webhook sink exists in the same dispatch table but is never reached unless `DELIVERY_SINK` is changed away from its default.
