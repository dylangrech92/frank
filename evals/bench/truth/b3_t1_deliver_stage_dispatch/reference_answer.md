`run_deliver` is defined in `relay/pipeline/orchestrator.py` -- that is the copy wired into the pipeline. It is never called by that literal name anywhere else. Instead, the module builds a `STAGE_DISPATCH` dict that maps each stage's string name to its handler function, including `"deliver": run_deliver`. `run_pipeline` never hard-codes calls to the five stage functions; it iterates over `STAGE_ORDER` and, for each stage name, looks up `stage_fn = STAGE_DISPATCH[stage_name]` and then calls `stage_fn(event)`. So during a normal run, `run_deliver` is reached only through that dict lookup plus indirect call, not through a `run_deliver(event)` call expression in the source.

Note there is a second, unrelated function also named `run_deliver` in `relay/handlers/delivery.py` -- it is a leftover pre-refactor copy that nothing imports or calls; it just happens to share the name and call `finalize_and_send` internally if it were ever invoked, which it isn't.

Because of that, a shallow search for literal `run_deliver(` calls turns up nothing outside two `def` lines and the dict entry, which is why it is easy to misjudge the real one as dead code -- but it genuinely runs on every successful pipeline pass, just via the dispatch table rather than a named call.
