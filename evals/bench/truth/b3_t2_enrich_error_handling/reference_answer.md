The `enrich` stage can fail in two different places, and `run_pipeline`'s except RelayError block in `relay/pipeline/orchestrator.py` catches RelayError from either one, then hands it to `retry.should_retry` to decide what happens next.

First, `load_plugin` (called with `config.ENRICHMENT_PLUGIN`) raises `PluginLoadError` if the named module cannot be imported, or if it does not expose a `PLUGIN` entry point. Second, once a plugin is loaded, its own `enrich` function can also raise `EnrichmentError` -- in the default `builtin_enricher` plugin, `EnrichmentError` is raised specifically when the order's payload has no postal_code to derive a shipping region from. Because both `PluginLoadError` and `EnrichmentError` are RelayError subclasses, the same except block in the orchestrator catches whichever one was raised.

`PluginLoadError` is one of the `RETRYABLE_EXCEPTIONS`, so a plugin-load failure gets scheduled for retry with backoff, up to `config.MAX_RETRIES` attempts, before it is eventually dead-lettered if it keeps failing. `EnrichmentError`, however, is not in `RETRYABLE_EXCEPTIONS` at all, so it is dead-lettered immediately on the very first failure -- it never goes through the scheduler, because a missing postal_code in the payload won't fix itself on a later attempt.

There is also a third, structurally different failure mode worth naming separately. `relay/handlers/audit.py` registers a second handler on `EVENT_ORDER_ENRICHED`, `flag_large_order`, alongside the existing `record_enrichment`. If the order's `qty` is at or above the large-order alert threshold, `flag_large_order` raises a plain `ValueError` -- not a `RelayError` subclass at all. This exception never reaches the orchestrator's except-RelayError block, and not only because it isn't a RelayError: it's raised from inside a handler invoked by `bus.publish`, and `EventBus.publish` catches every handler's exceptions itself (broadly, not just RelayError), logs a warning, and moves on to the next handler. So a `flag_large_order` failure is logged and the event keeps flowing through the pipeline as if nothing happened -- it is never retried and never dead-lettered, unlike either `PluginLoadError` or `EnrichmentError`.
