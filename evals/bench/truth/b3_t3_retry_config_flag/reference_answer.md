The flag that governs whether a failed event is retried at all is `config.RETRY_ENABLED`, a plain boolean switch. It is checked first, before anything else, inside `should_retry` in `relay/pipeline/retry.py`: the very first line of the function is `if not config.RETRY_ENABLED: return False`, so when the flag is off, no other condition in the function even gets evaluated.

This is different from `config.MAX_RETRIES`, which only caps how many retries are allowed once retrying is already permitted -- it's a threshold on attempt count, not a switch for whether the retry path runs at all. If the `RETRY_ENABLED` check were deleted from `should_retry`, the function would simply fall through to the remaining checks: whether the attempt count is under `MAX_RETRIES`, and whether the exception type is one of `RETRYABLE_EXCEPTIONS`. In other words, retries would always be attempted for any retryable failure, up to the configured cap, and there would be no way left for an operator to globally disable retrying through configuration -- the kill switch itself would be gone, not just weakened.

Note also `config.REPLAY_ENABLED`, defined right next to `RETRY_ENABLED` in `config.py` and easy to mistake for it given the similar name -- it is unrelated to automatic in-pipeline retry. It only gates whether `main.py replay` can pull dead-lettered events back through the pipeline at all; deleting it would disable the CLI replay command, not the pipeline's own automatic retry behavior.
